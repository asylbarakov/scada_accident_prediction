# Подключение прогноза отказа CARE H7 к WindScope

Дата проверки: 17 ноября 2026 года. Область работы: inference существующей модели и интеграция с историческим replay. Новое обучение и классификация типа отказа не выполнялись.

## Результат

WindScope подключён к сохранённому pipeline Logistic Regression из `project/results/care_h7_windows_20261116/training/h7/logistic`. Прогноз рассчитывается worker по доступной истории измерений, сохраняется в PostgreSQL и передаётся через WebSocket. Архивные прогнозы не подставляются вместо вычислений.

Задача модели: бинарный сигнал о возможном аннотированном отказе в следующие **168 часов**. Это не точное время отказа, RUL, диагноз узла или калиброванная вероятность. Обозначение H7 означает семь суток; исходная частота SCADA — 10 минут, частота расчёта этой модели — один час, на целой границе часа исходной шкалы.

Исследовательский проект сохранён отдельно. Его исходники, CSV и обученные модели не изменялись. Описание исходного эксперимента: [отчёт](../project/results/care_h7_windows_20261116/report.md), [конфигурация](../project/configs/care_h7.json), [метрики](../project/results/care_h7_windows_20261116/training/metrics.csv).

## Что именно переиспользовано

1. Сохранённый pipeline: median imputation → StandardScaler → Logistic Regression. Масштабирование выполняет сам pipeline.
2. Порядок 210 признаков и порог `0.9999999614086562` из `inference.json`.
3. Исходный алгоритм `scada_pdm.preparation.make_features`, который копируется в образ из исследовательского проекта без редактирования. CARE-политика наблюдаемости сохранена: достаточно хотя бы одного доступного физического канала, пропуски отдельных признаков обрабатывает обученный imputer.
4. Существующие механизм replay, ревизии команд, lease, PostgreSQL, WebSocket и жизненный цикл предупреждений WindScope.

Новый код адаптера находится в [forecast/inference.py](../forecast/inference.py); HTTP-контракт — в [forecast/server.py](../forecast/server.py). Worker не импортирует scikit-learn H7 и не загружает joblib.

## Причинность и история

Для времени расчёта `t` worker извлекает из **того же сценария** измерения на отрезке `[t − 168 часов, t]`. В сервис передаются только `asset_id`, `source_time` и список физических измерений. Идентификаторы событий, partition, status_type_id, fault labels и даты отказов не входят в inference payload.

Адаптер выбирает десять каналов, преобразует их в `float32` и вызывает исходный feature builder. При задержке в один шаг последнее используемое измерение относится к `t − 10 минутам`. Измерение текущего шага `t` не участвует в значениях признаков. Окна: 1, 6, 24 и 168 часов; статистики: now, mean, max, std, delta_mean, trend.

Минимальная непрерывная история — 24 часа. Пока полной недельной истории нет, недельные признаки могут быть пропущены; это соответствует исходному pipeline и его imputer. Разрывы не заполняются синтетическими измерениями. После разрыва готовность истории рассчитывается заново.

История до начала выбранного диапазона replay доступна для признаков, поскольку эти измерения уже относятся к прошлому. Будущие измерения не выбираются SQL-запросом и дополнительно запрещены адаптером. Сервис не имеет доступа к файлам аннотаций.

Исходная timezone CARE неизвестна. В интерфейсе и контракте используется исходная шкала времени без timezone. UTC у `processed_at` относится к времени обработки, а не к подтверждённой timezone измерений.

## Контракт результата

Пример при расчёте в `2023-08-12 10:00:00`:

```json
{
  "status": "ok",
  "model_id": "care-h7-logistic-20261116",
  "predicted_class": 1,
  "class_1_score": 0.9999999998243527,
  "threshold": 0.9999999614086562,
  "score_semantics": "uncalibrated_failure_score",
  "prediction_horizon": "P7D",
  "prediction_horizon_hours": 168,
  "prediction_interval_start": "2023-08-12 10:00:00",
  "prediction_interval_end": "2023-08-19 10:00:00",
  "feature_cutoff": "2023-08-12 09:50:00"
}
```

`prediction_interval_end` — граница горизонта, **не предсказанная дата поломки**. `predicted_class` — бинарное превышение порога; это не класс сломанного компонента.

Состояния `warming_up`, `unavailable`, `data_gap` не трактуются как отрицательный прогноз. Между почасовыми расчётами новые predictions не создаются: последнее значение хранит своё исходное время. Интерфейс помечает результат как устаревший через час исходного времени. Изменение скорости replay не меняет модельный горизонт или частоту расчётов в шкале SCADA.

## Сессии и предупреждения

Миграция `003` добавляет `ReplaySession.model_id`. Существующие сессии остаются привязанными к прежнему XGBoost. Новые сессии через API по умолчанию используют H7; модель можно явно выбрать в настройках нового запуска. В рамках одного поколения результаты разных моделей не смешиваются.

Для H7 используются исходный порог и политика по умолчанию: один positive для активации, один negative для закрытия, cooldown 0 минут. Это сохраняет поведение порога эксперимента, не добавляя задержку подтверждения. Пользователь может создать новую сессию с другой политикой, но метрики исходного эксперимента нельзя автоматически переносить на такую политику.

Промежуточные SCADA-точки не закрывают предупреждение и не увеличивают число расчётов в нём. Недоступность нового прогноза или разрыв данных прерывают активное предупреждение с причиной качества/разрыва, а не с подтверждением нормальной работы. История и принятые предупреждения сохраняются. Сброс replay создаёт новое поколение и скрывает прежние прогнозы из текущего запуска.

Для H7 не вызываются эвристики классификации узла. `suspected_subsystem` остаётся `null`; карточка показывает прогноз отказа, score и границу горизонта вместо предположения о причине. Измерения доступны на отдельном графике.

Добавленные CSV: 54 010 строк в Event 13, 53 036 в Event 22, 54 082 в Event 72. Контрольные суммы закреплены в [манифесте](../data/h7_scenarios_manifest.json); импорт повторяемый и не дублирует строки. Три события турбины 21 отображаются как сценарии одного оборудования, а не как три разные турбины.

В сохранённом эксперименте Logistic Regression обнаружила **1 из 2** тестовых эпизодов. Для Event 22 первый сигнал — `2023-08-12 10:00`, аннотированный отказ — `2023-08-19 10:00`, наблюдённый lead time — 168 часов. Второй эпизод пропущен. Подключение к WindScope не улучшает эти метрики само по себе.

Порог очень близок к единице; интерфейс сохраняет достаточную точность score и не показывает его как процент. Высокий score ниже порога возможен и не является основанием менять порог на тестовых событиях.

Ноль ложных тревог в исходном test относится к 333 часам отрицательной экспозиции, то есть приблизительно 0,456 турбина-месяца. Это не доказательство низкой частоты ложных тревог в промышленной эксплуатации. Тестовая турбина одна; эпизодов два. Повторяющиеся часовые окна коррелированы.

Live replay рассчитывает score и на доступных точках вне отобранных окон с проверенной целевой меткой. Для них не присваивается выдуманная ground truth и не заявляются метрики. Устойчивость на другом парке, новых датчиках, после ремонта или на полностью непрерывной эксплуатации не подтверждена.

## Окружение и изоляция

Отдельный образ `windscope-h7:1.0`: Python 3.12.12, numpy 2.3.5, pandas 2.3.3, scipy 1.16.3, scikit-learn 1.8.0, joblib 1.5.3. Полный закреплённый набор: [requirements.lock.txt](../forecast/requirements.lock.txt). Версии численных библиотек совпадают с сохранённым экспериментом; переход с Python 3.14 Windows на Python 3.12 Linux проверен воспроизведением score.

LightGBM и Streamlit не нужны для выбранного Logistic Regression pipeline. PyArrow используется для проверки архивов, openpyxl требуется импортом исходного модуля подготовки данных. Дополнительное обучение не требуется.

Joblib остаётся исполняемым сериализованным форматом. SHA-256 `60836ffb2881ab639d8507483a0a2be6a5dd0c5b9067f2c94943ca56f97bb892` проверяется перед загрузкой; это проверка идентичности, а не доказательство безопасности. Первичная проверка выполнялась без сети, под непривилегированным пользователем, с read-only файловой системой, ограничениями памяти/CPU/PID и без credentials.

Рабочий сервис имеет только внутреннюю сеть inference, без опубликованного порта и внешнего выхода. Ему смонтированы read-only только pipeline, inference manifest и config. CSV, архивы прогнозов, БД и её credentials в этот контейнер не передаются. Worker отправляет физические данные через HTTP. При замене артефакта потребуется отдельная проверка, обновление контрольной суммы и повторное воспроизведение результатов.

## Запуск и проверка в интерфейсе

Из корня проекта:

```powershell
docker compose up -d --build
./scripts/test_h7.ps1
```

Предполагается подготовленный базовый образ проекта. Полный исходный способ запуска с его подготовкой: `./scripts/start_app.ps1`.

Открыть `http://localhost:3100`, выбрать Event 22 и страницу «Турбина». В настройках нового запуска выбрать «Прогноз отказа H7 · Logistic Regression», диапазон `2023-08-12 09:50` — `2023-08-12 12:00`, создать сессию и запустить replay. При скорости 36 000× отрезок проходит за несколько секунд.

Проверяемые признаки работы: движется время набора и счётчик измерений; в 10:00 появляется новый H7-прогноз и предупреждение; время последнего прогноза меняется только на границе следующего часа; в карточке указан горизонт семь суток и точное время расчёта. При обновлении страницы сессия и прогноз восстанавливаются из backend.

Для нормального случая можно создать диапазон Event 13 `2023-05-03 14:00` — `14:20`. Отсутствие предупреждения означает только непревышение порога.

## Следующие шаги

Сначала оценить H7 на более длинном непрерывном replay и независимых эпизодах, отдельно измеряя пропуски, готовность истории, предупреждения и отрицательную экспозицию. Если нужны горизонты 6/24 часа, потребуется новая разметка будущих интервалов и отдельное обучение с независимой проверкой. Классификация компонентов остаётся вне текущей интеграции.
