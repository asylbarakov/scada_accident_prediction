# Демо раннего предупреждения WindScope · 17.11.2026

## Что запущено

Основной экран: [http://localhost:3100](http://localhost:3100). Расширенный предыдущий интерфейс: [http://localhost:3100/monitoring](http://localhost:3100/monitoring). API: [http://localhost:8100/docs](http://localhost:8100/docs).

Это исторический replay реальных CARE v6 измерений. Персональные XGBoost normal-behaviour модели вычисляют температурные отклонения **во время replay**, а не читают готовый CSV с предсказаниями. Модель получает до восьми часов физических измерений, заканчивающихся текущим временем; последний используемый датчик относится к t − 10 минут. Future labels, status и аннотации в inference не передаются. Runtime не имеет доступа к dataset annotations, БД или CSV будущих predictions.

## Как показать за несколько минут

1. Выберите «Раннее предупреждение», отрезок №26. Нажмите «Запустить».
2. При обычной скорости одно 10-минутное измерение идёт каждые две секунды; расчёт ML — каждый час истории, примерно каждые 12 секунд. Видны часы набора, число измерений, число успешных расчётов и задержка inference.
3. Около 08:00 по часам набора индекс пересечёт 1,0. Появятся предупреждение и конкретные температуры: измерено, нормальное ожидание, разница. Индекс — отношение score к персональному порогу, **не процент вероятности**.
4. «Принять в работу» сохраняет acknowledgement. Снижение score или недоступность нового расчёта не закрывают наблюдение. Оно хранится 24 часа после последнего сигнала; это отдельная operational policy, не улучшение ML recall.
5. При достижении 10:20 откроется историческая отметка отказа. Проверка покажет предупреждение за **2 ч 20 мин**. Метка отказа — конец CARE anomaly interval; это не диагноз модели.
6. «Сравнить с известным будущим» раскрывает историческую отметку раньше и добавляет серую пунктирную линию будущих **реальных измерений**. Режим явно подписан; эти данные не используются моделью. Будущая линия не является sensor forecast.
7. После конца выбранного интервала replay повторяется. Циклы и исходные даты подписаны; повтор не создаёт новых независимых тестов.

Дополнительные примеры:

- №25 «Нормальная работа»: 73 измерения, 13 ML-расчётов, без предупреждений в выбранном контрольном отрезке.
- №42 «Длинное упреждение»: сигнал за **14 ч 50 мин**. Позже score падает, но событие остаётся на контроле.
- №0 «Пропущенный отказ»: демонстрирует ограничение; после наступления исторического отказа UI прямо сообщает, что раннего сигнала не было.

Сценарии подобраны для демонстрации. На полной прежней исторической проверке персональный подход дал **4/11 отказов**, **17 ложных эпизодов на 2 983 normal-часа**, семь пропусков. Независимого внешнего теста пока нет. [Полный отчёт персонального эксперимента](personal_h24_experiment.md).

## Что изменено

- Изолированный сервис `personal` с native UBJSON regressors и JSON calibration; никаких внешних pickle для этой модели.
- Registry из четырёх проверенных исторических baselines. Только native files, прошлые границы, threshold и SHA256; future annotations и prediction CSV при экспорте не копируются.
- API выбора demo-сценария, временная доступность ground truth, hourly inference routing через worker.
- Watch policy не считает отрицательный/недоступный score подтверждением устранения неисправности. При начале нового исторического цикла старый watch закрывается с причиной `dataset_replay`.
- Новый основной UI: четыре понятных сценария, управление скоростью, два работающих графика, доказуемая активность модели, объяснение по датчикам и отдельная проверка по истории.
- Старый мониторинг сохранён по `/monitoring`.

## Проверка

- 43 backend unit-теста, включая physical-only payload, ограничение прошлых восьми часов, скрытие будущего и сохранение watch.
- 12 frontend logic-тестов: freshness, индекс без процентов, pacing и различие текущего score/удержанного наблюдения.
- Три real-data runtime-теста: online prefix Event 26 совпадает с frozen experiment; будущие строки, чужой asset и labels отклоняются; недостаток истории даёт unknown.
- Next.js production build с TypeScript проходит.
- Live API→worker→model→database проверка четырёх сценариев: 26 — 61 измерение/11 расчётов, 25 — 73/13, 0 — 67/12, 42 — 115/20. Упреждения 2:20 и 14:50 совпадают с проверенным экспериментом.
- При speed 300 четыре измерения занимают около 6,26 с: поток не выдаётся мгновенной пачкой. Непрерывный replay прошёл второй цикл.
- UI проверен в браузере на desktop и мобильной ширине; просмотрены графики, предупреждение, acknowledgement и явное раскрытие исторического будущего.

## Запуск

В подготовленном текущем workspace достаточно `docker compose up -d`. Для подготовки новой установки:

```powershell
Set-Location <каталог-WindScope>
.\scripts\start_demo.ps1
```

Нужны Docker Desktop (Linux containers), Git, Python 3 и сеть для первой подготовки. Скрипт проверяет/fetches только нужные CARE CSV через HTTP ranges, сверяет SHA256, проверяет оригинальный research release, подготавливает pinned wheels/images и запускает Compose. Raw CSV, Python environments и wheelhouse не должны храниться в Git. Native runtime registry включается в поставку. Подготовка никогда не переобучает модель.

Dataset attribution: Christian Gück, Cyriana Roelofs, *Wind Turbine SCADA Data For Early Fault Detection*, CARE v6, [Zenodo 15846963](https://zenodo.org/records/15846963), CC BY-SA 4.0; [описание CARE](https://www.mdpi.com/2306-5729/9/12/138). Полные условия и источники — `project/DATA_LICENSES.md`.

Перезапуск worker сохраняет историю сессий и восстанавливает прерванные сессии на паузе. Для продолжения нажмите «Продолжить». Открытая PostgreSQL база не удаляется.
