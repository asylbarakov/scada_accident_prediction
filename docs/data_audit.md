### CARE: факты

- Release v6 (2025-07-09): 36 турбин, три парка, 95 датасетов, 89 лет суммарно; 45 событий с подтверждённым anomalous interval до отказа и 50 нормальных. Частота 10 минут. Wind Farm A — 22 dataset files, 86 features; B — 257; C — 957.
- В каждой выборке примерно год *train* и ограниченный *prediction* отрезок (по статье 4–98 суток). Разметка `event_label` относится к событию; `status_type_id` — к состоянию отдельной точки.
- **В статье сформулировано однозначно:** `event_start` — начало аномального интервала; **`event_end` — начало отказа турбины**. Не путать при формировании supervised target.
- В Wind Farm A `status_type_id=4` отмечает 14 суток **перед** отказом, `status_type_id=3` — 3 суток **после** него, эти метки вычислены ретроспективно из fault log. Значит, `status_type_id` нельзя подавать модели и нельзя использовать, чтобы отфильтровать точки при тестировании нашей задачи. Для обучения baseline датчиков он может служить только исторической очисткой *после того, как его происхождение явно задокументировано*; предпочтительнее фильтрация наблюдаемыми показателями (мощность/ветер).
- Для B/C status отражает operator status (по-разному интерпретировать), но это всё равно не fault-within-7/30 target.
- В файлах одной турбины после анонимизации возможны пересекающиеся даты, а порядок событий не восстановим. Нельзя строить единый `sort(timestamp)` across files.
- По примечанию v6 данные Min/Max/Std часто недостоверны; **начать с `_avg`**, проверить углы и пропуски.
- Весь CARE: ZIP ~5,5 ГБ, распаковка ~19–20 ГБ. Для первичного baseline достаточно Wind Farm A, но архив скачивается целиком, если нет другого официально доступного частичного пути.

### Семантика supervised target

Для **документированного** отказа `f=event_end` и момента `t < f`:

`y_H(t)=1` если `t < f <= t+H`, иначе `0`, *только когда подтверждено отсутствие других сбоев на интервале наблюдения*.

Для нормального события `y_H(t)=0` допустимо **только если до `t+H` существует наблюдаемый/надёжно размеченный будущий отрезок без отказа**. Иначе `UNKNOWN` (right-censored), а не `0`. Точки `t>=f` исключать из предсказания *до* следующего документированного корректного восстановления.

Принципиальное ограничение: «нет события в разметке» не равно «гарантированно нет отказа». Проверить, какие варианты `normal` были вручную подтверждены и насколько длинные их интервалы.

### Разделение и leakage

- **Запрещено:** случайно разрезать соседние 10-минутные точки по train/test.
- Группировать по **event_id** для первичного теста; дополнительно проверять **leave-one-asset-out** (Wind Farm A всего 5 турбин). Желательно держать отдельный untouched test и при необходимости вложенную CV для выбора гиперпараметров/порогов.
- У CARE разные event-файлы одной турбины могут содержать совпадающие/анонимизированные исторические периоды. `GroupKFold(event_id)` сам по себе **не гарантирует** независимость по оборудованию и реальным датам.
- Нормализация / импутация / отбор фичей / калибровка вероятностей / выбор порогов — **только внутри train-fold**, не по всему SCADA corpus, не по склеенной training+test истории.
- Для streaming prediction признаки доступны только из прошлого до текущего момента t. `rolling(..., center=True)` и глобальные future-based z-score запрещены.
- Нельзя превращать откалиброванный «anomaly score» непосредственно в проценты отказа.
- Из-за отбора события benchmark prevalence 45/95 не равна эксплуатационной частоте реальных отказов. Для реального deployment потребуется адаптация базовой вероятности и проверка на хронологических производственных данных.

## 2. Аудит стороннего кода

### 2.1 EnergyFaultDetector — https://github.com/AEFDI/EnergyFaultDetector

- Посмотрены `README.md`, `pyproject.toml`, `energy_fault_detector/evaluation/care2compare.py`, `energy_fault_detector/main.py`.
- MIT; Python `>=3.10,<3.13`, TensorFlow `>=2.15` (версия зависит от Python), `pandas<3`, `numpy<2`, scikit-learn `>=1.5.2,<=1.7.0`.
- `pip install energy-fault-detector`; CLI `quick_fault_detector <path_to_csv> --c2c_example`; программная загрузка CARE через `Care2CompareDataset(path=..., download_dataset=False)`.
- **Важно**: `--c2c_example` означает демо **на одном CSV**, а не готовый 7/30 классификатор или 95-event production pipeline. При `download_dataset=True` лоадер может автоматически скачать несколько гигабайт — использовать `False`.
- Для Windows/WSL создать отдельное окружение **Python 3.11**; в текущем sandbox Python 3.13.5 не соответствует требованиям.
- Годится для получения аномальности и объяснимых residual-признаков, если они строятся без подсматривания будущего.

### 2.2 CARE PDM v2 — https://github.com/PeterImoniose/care-wind-turbine-predictive-maintenance-v2

- Прочитаны `README.md`, `pyproject.toml`, `src/carepdm/data.py`, `src/carepdm/preprocess.py`, `configs/default.yaml`.
- MIT, Python >=3.10, PyTorch, Pandas, PyArrow, sklearn. `python -m carepdm prepare|detect|evaluate|diagnose|report` после `pip install -e .[dev]` и `CAREPDM_RAW_DIR=...`.
- Использует `_avg` данные, сенсорную разметку, Parquet float32, blocked validation, fit-transform по train-части каждого события. Это полезный инженерный baseline.
- Не решает нашу задачу 7/30 напрямую. Автор сообщает CARE ~0.619 для conditional overall, это **его** результат, не наш.
- Конфиг `raw_dir` задан примером абсолютного Windows-пути — обязательно заменить переменной окружения, не переносить как есть.

### 2.3 14-day supervised notebook — https://github.com/diegotamargo/Wind-turbine-failure-predictor

- Прочитан целиком `notebooks/wind_turbine_failure_prediction.ipynb`: ключевые ячейки 3, 9, 15, 16, 18, 22, 24, 30.
- **Критично (cell 9)**: `warning_start = event["event_start_id"] - HORIZON_DAYS * ROWS_PER_DAY`; target ставится до `event_start_id`. По официальной статье `event_start` — аномалия, `event_end` — отказ. Значит, baseline предсказывает **начала аномальных окон**, а не гарантированно **физический отказ через 14 дней**.
- **Критично (cell 9)**: `operating = ...status_type_id.isin([0, 1, 2])` исключает будущим fault-log размеченный интервал Farm A (включая `status_type_id=4`). Это **не допустимый online-фильтр** для независимого Failure Prediction.
- **Неэксплуатационный threshold (cell 30)**: `alert_threshold = quantile(forest_probability[y==0], .99)` использует OOF-предсказания и метки всех CV-событий, включая тестируемое, при визуализации алертов и расчёте lead time. Выбирать порог нужно на независимом training/validation.
- **Слабая независимость**: GroupKFold сгруппирован по `event_id`, не по турбине, и не решает риск повторных исторических данных одного asset в анонимизированных файлах.
- **Два разных вопроса**: cell 24 сравнивает общий риск *любого* отказа с меткой конкретного узла; опубликованные «gearbox 0.98 ROC-AUC» не являются качеством обученного отдельного gearbox-классификатора.
- README заявляет ROC-AUC 0.68 / PR-AUC 0.088 для RF на 14 days. Эти цифры **не воспроизведены и не принимаются как baseline нашего проекта**.
- В корне GitHub проекта на момент просмотра не обнаружена LICENSE; публичный доступ к коду сам по себе **не даёт разрешения на копирование/модификацию**. Использовать только общие методы, свои реализации.

## 3. Альтернативный источник EDP

EDP SCADA (Mendeley Data v2, опубликована 2026-08-28): четыре турбины T01/T06/T07/T11, 2016–2017 гг., 10-минутные показания, 83 признака на турбину, ~28 записей подтверждённых отказов, ~256 тыс. записей operational alarms, 10 Excel-файлов, ~173,7 МБ, лицензия CC BY 4.0.

Здесь **лучше выражена хронология**, поэтому потенциально более обоснован именно fixed-horizon supervised classifier. Однако мало независимых отказов (28 всего): невозможно обещать надёжную оценку 30-дневных вероятностей по многим видам оборудования. Проверить `failure_timestamp`, repair/downtime, множественные отказы, пропуски и границы наблюдения до создания меток. Возможен отличный демонстрационный *event-risk score* с аккуратно ограниченным статусом исследовательского прототипа.

## 4. Рекомендация и decision gate

1. Прочитать **реальные** `event_info.csv` и проверить 22 Wind Farm A CSV (начать с metadata-only, затем scan-series). Скрипт `scripts/care_readiness_audit.py` выводит потенциальное число positive/negative/censored окон на H=7,30.
2. Ручная проверка на 3–5 событиях: `event_end` совпадает со стартом документированного отказа? Действительно ли нормальное событие покрывает полный будущий горизонт? Есть ли скрытые fault-log записи?
3. Если большая часть H=30 не покрыта или события дают неоднозначный target, взять **EDP** как основной supervised, а CARE + EnergyFaultDetector оставить для anomaly detection. Это архитектурно допустимо — один dashboard может показать risk model и anomaly score раздельно.
4. До решения data gate не обучать модель, не делать demo «вероятность отказа 7/30» на псевдоразметке.
