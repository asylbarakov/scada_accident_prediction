# План реализации SCADA PDM MVP

Дата: 2026-11-16. Режим: исследовательский демонстратор, не промышленный диагностический инструмент.

## Целевой сценарий

Пользователь выбирает турбину, день наблюдения и горизонт **7/30 дней**. Система показывает физические значения датчиков, риск неисправности в ближайшем горизонте (после калибровки), относительную аномальность (отдельная шкала) и журнал предупреждений. Историческое воспроизведение не должно использовать события, ещё не наступившие к дате на экране.

## Этап B — данные и признаки

Реализация EDP, проверки разметки и разбиения и Parquet-кеш прошли технический прогон. Справочный фрагмент не дал пригодных размеченных окон. Полнота оригинальных рядов и журналов EDP требует проверки. [Аудит EDP](edp_data_audit.md)

- [ ] Standalone loader (`pandas`, `pyarrow`): один источник / одна хронология; не смешивать анонимизированные event timeline.
- [ ] QC: пропуски, `_avg`, физические диапазоны, углы `sin/cos`, мощность/ветер, циклические часы/сезон при обосновании.
- [ ] Causal features: лаги, rolling mean/std/min/max/slope за 1, 6, 24 ч, 7 суток; строго past-only.
- [ ] Labeler H=7/H=30: event_end/EDP failure log; censored→exclude; near-fault post-event exclusion/cooldown.
- [ ] Train/val/test по целым событиям/турбинам/времени, без дублей между fold.
- [ ] Документировать сколько положительных **событий**, не только строк (смежные точки не независимы).

**Критерий:** воспроизводимый manifest событий, parquet features, unit tests на отсутствие future leakage.

## Этап C — модели и оценка

Сохранение Logistic Regression и LightGBM, повторный инференс, метрики и TreeSHAP проверены ограниченным синтетическим запуском H7/H30. Полноценный эксперимент на оригинальном EDP предусмотрен в [Colab](../notebooks/SCADA_Training_Colab.ipynb) после проверки покрытия каждого горизонта.

- [ ] Наивный baseline: константный риск / простая логистическая регрессия.
- [ ] LightGBM (или XGBoost) на обеих целях. Тюнинг только по train/val.
- [ ] Измерять PR-AUC/ROC-AUC на test, event recall, false alarms per turbine-month, median lead time, recall at fixed alarm burden.
- [ ] Калибровка вероятностей на независимой validation; если не хватает отказов — показывать «risk score», не проценты.
- [ ] Абляции: status leakage guard, без `event_start`, удаление near-fault дней, sensitivity to H and train split.
- [ ] Опционально anomaly-based features / energy-fault-detector в отдельном Python3.11 окружении.

**Критерий:** метрики на отложенных событиях + воспроизводимый `joblib` + конфиг + event prediction table.

## Решение по вычислительным ресурсам

- Logistic Regression / LightGBM на агрегированных признаках можно начинать на CPU.
- Установка EnergyFaultDetector/TensorFlow тяжелее и требует Python 3.10–3.12; запускать **после** data gate.
- Не требуется GPU/Transformer на первой итерации. Оптимизацию делать только если baseline слаб.

## Stop conditions

- Нельзя подтвердить дату отказа → **не** заявлять failure prediction.
- H30 не имеет корректных отрицательных и положительных независимых примеров → оставить H30 как experimental/unavailable, сфокусироваться на H7 или сменить dataset.
- Слишком мало независимых отказов для калибровки → выводить качественный score + неопределённость, не проценты.
- Отказ обнаруживается лишь из постфактум статуса → исключить такой признак и перерассчитать метрики.
