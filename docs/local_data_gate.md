# Локальный аудит CARE v6 · Wind Farm A

16 ноября 2026 года. **H7 подходит для исследовательского эксперимента после сверки эпизодов отказа и разбиения по турбинам. H30 не проходит проверку покрытия.** Для задачи с обоими горизонтами следующий кандидат — исходный EDP SCADA с журналом отказов.

## Среда и происхождение данных

- Проверка выполнена на Windows с Python 3.14.6. `py -3.11 --version` не нашёл установленный Python 3.11. Аудит рассчитан на Python 3.10+ и использует стандартную библиотеку. В Google Colab подготовлен тот же сценарий запуска, проверка выполнена в локальной среде. ML-зависимости и модели относятся к следующим этапам.
- На C: перед загрузкой было **9,13 ГБ** свободно, после проверки — **7,84 ГБ**. Полный архив и его распакованное содержимое потребовали бы вместе около **24,5–25,5 ГБ**.
- Из оригинального ZIP по HTTP Range получены **только файлы Wind Farm A**. Прочитано 158 063 049 байт по сети, сохранено 802 870 209 байт в 24 файлах. Все 22 SCADA CSV, `event_info.csv` и `feature_description.csv` прошли проверку CRC-32 по ZIP. Повторная проверка уже полученных файлов потребовала 13 990 сетевых байт. MD5 всего архива опубликован отдельно. [Карточка CARE v6](https://zenodo.org/records/15846963) · [Оглавление ZIP](https://zenodo.org/records/15846963/preview/CARE_To_Compare.zip?include_deleted=0)

## Покрытие меток на реальных рядах

Проверены 22 сегмента на пяти турбинах с ID 0, 10, 11, 13 и 21. В метаданных Wind Farm A 12 событий `anomaly` и 10 `normal`. Для всех 22 совпали `event_start` и `event_end` с временными метками строк по соответствующим ID в `prediction`. Просканированы 1 146 154 строки `train` и 50 593 строки `prediction`. В 11 сегментах найдено 33 нарушения 10-минутного шага. Внутри `prediction` дубликатов timestamp не обнаружено.

| Горизонт | Положительные строки | Отрицательные строки | Цензурировано | Исключено | События с положительными / отрицательными строками |
| --- | ---: | ---: | ---: | ---: | ---: |
| 7 дней | 12 021 | 8 428 | 20 388 | 9 756 | 12 / 10 |
| 30 дней | 20 454 | 0 | 20 383 | 9 756 | 12 / 0 |

- Положительная метка возможна при `t < event_end <= t + H` в файле с документированным отказом. Отсчёт ведётся от начала зарегистрированного отказа. `event_start` задаёт начало аномального интервала. [Статья CARE, §3.1](https://www.mdpi.com/2306-5729/9/12/138#sec3dot1-data-09-00138)
- Ноль присваивается, когда весь горизонт лежит в явно размеченном нормальном интервале и наблюдается с шагом 10 минут. Ранние точки в `anomaly` цензурированы при отсутствии подтверждения, что окно свободно от других отказов. Из них 5 440 строк на H7 образуют непрерывные окна до известного отказа и требуют сверки с исходным журналом. На H30 таких непрерывных окон нет.
- В категорию «исключено» попали строки с момента отказа и точки из padding вне размеченного нормального интервала. Каждая строка `prediction` входит ровно в одну из четырёх категорий для каждого горизонта.
- Самый длинный размеченный нормальный интервал — **20 дней 22 часа 10 минут** (событие 3). Даже если считать всё нормальное `prediction` вместе с padding, максимум составляет **24 дня 21 час** (событие 13). H30 остаётся без отрицательного класса. Событие 40 даёт 366 строк раньше чем за 30 дней до отказа. Их окна пересекают разрывы SCADA, а отсутствие иных отказов требует подтверждения.
- Числа отражают покрытие разметки по файлам. В 12 положительных сегментах представлены пять турбин, а число независимых физических эпизодов ещё предстоит установить.

Совпадение timestamps и ID подтверждает согласованность границ файлов. Привязка к физическому эпизоду, отдельным компонентам и моменту восстановления требует исходного журнала. Например, мощность в событии 0 на строке `event_end` остаётся ненулевой.

## Проверка утечек и требования к разбиению

- В **38 парах** файлов одной турбины пересекаются диапазоны времени, если учитывать `train` и `prediction`. Для событий 0 и 26 подтверждено точное совпадение всех **2 838** строк `prediction` события 0 с частью `train` события 26 по timestamp и всем **46** колонкам `_avg`.
- Для 51 и 72 подтверждено **1 918** одинаковых строк `prediction` по timestamp и всем 46 `_avg`. У двух разметок отказа одной турбины разница 7 ч 30 мин, а восстановление между ними не подтверждено. Эти события нужно оставить в одной группе и сверить как потенциально единый эпизод. До сверки строки между якорями нельзя считать чистыми предаварийными наблюдениями второго события.
- `status_type_id` в Wind Farm A реконструирован по журналу отказов. Он исключается из признаков, импутации и фильтра строк для обучения и оценки модели. Аналогично исключаются `event_label`, границы события и их ID, `train_test`, локальный ID строки, расстояние до границ файла и признаки будущего покрытия. Аудит использует метаданные для проверки разметки и игнорирует статус и значения датчиков при подсчёте. Замена статуса между 0, 3 и 4 покрыта тестом. [Описание разметки CARE](https://www.mdpi.com/2306-5729/9/12/138#sec3dot1-data-09-00138)
- Для H7 заранее зафиксировать разбиение по целым турбинам, проверить дубли телеметрии между folds и хранить каждый анонимизированный файл отдельно. Все лаги и агрегаты брать из данных до момента `t` внутри файла. Импутацию, нормализацию и отбор признаков обучать внутри train-fold, пороги и калибровку выбирать на отдельной validation. Результаты оценивать по эпизодам и турбинам с учётом их малого числа.

## Следующий шаг для H7 и H30

У [EDP SCADA v2](https://data.mendeley.com/datasets/zjxjnjp3xs/2) есть два года временных рядов по четырём турбинам, 10-минутный шаг и 28 записей подтверждённых отказов. Это версия с предварительно фильтрованными вариантами SCADA, поэтому для воспроизводимой проверки предпочтительнее исходная телеметрия и годовые журналы из [каталога EDP](https://edp.com/en/innovation/data). Опубликованная процедура фильтрации удаляет наблюдения по статистике кластеров, поэтому надо установить, на каких периодах она была подогнана и какие отсчёты удалены. [Статья о фильтрации](https://www.mdpi.com/1996-1073/18/22/5954)

Следующий эксперимент — инвентаризировать исходные файлы EDP 2016–2017, проверить границы полноты журналов, привязку записей к турбинам, повторные записи, время восстановления и разрывы в SCADA. Затем пересчитать H7/H30 по ближайшему подтверждённому отказу в хронологии каждой турбины с цензурированием неполных окон. CARE A происходит из EDP, поэтому эти источники могут содержать общие физические эпизоды и не должны использоваться как независимые train/test-корпуса без проверки соответствия.

## Полный архив CARE v6

Команды PowerShell приведены на случай, если позже понадобится весь архив. Для текущей проверки достаточно частичной загрузки Wind Farm A. Запускать из каталога проекта на диске с запасом минимум **26 ГБ**. [Размер файла и официальный MD5 на Zenodo](https://zenodo.org/records/15846963)

```powershell
New-Item -ItemType Directory -Path data -Force | Out-Null
$archive = 'data/CARE_To_Compare.zip'
$partial = "$archive.part"
$expected = '2547b58c21ac8c242d13232860cf500c'
if (-not (Test-Path -LiteralPath $archive)) {
    curl.exe --fail --location --retry 3 --continue-at - --output $partial 'https://zenodo.org/records/15846963/files/CARE_To_Compare.zip?download=1'
    if ($LASTEXITCODE -ne 0) { throw 'CARE download failed' }
    if ((Get-FileHash -LiteralPath $partial -Algorithm MD5).Hash -ne $expected) {
        throw 'CARE v6 checksum mismatch'
    }
    Move-Item -LiteralPath $partial -Destination $archive
}
if ((Get-FileHash -LiteralPath $archive -Algorithm MD5).Hash -ne $expected) {
    throw 'CARE v6 checksum mismatch'
}
New-Item -ItemType Directory -Path data/full_release -Force | Out-Null
tar.exe -xf $archive -C data/full_release
if ($LASTEXITCODE -ne 0) { throw 'CARE extraction failed' }
```
